# Showcase video — how to edit it without five correction rounds

The showcase is built from data: session scripts drive a real editor frame by
frame (`project/showcase/sessions/*.gd` against `showcase_director.gd`), the
frames are cut by an EDL (`showcase_video/edl*.toml`, the v2 ones generated by
`showcase_video/tools/gen_edl_v2.py`) and `build.sh` assembles the cuts. The
pipeline overview is in CLAUDE.md's Key Documents; this file is the working
method, written after rounds where the owner, not the agent, found every
problem by watching the video.

## Render on the GPU box, not locally

```bash
PB_SHOWCASE_LAYOUT=showcase_video/layouts/tour.cfg \
  ./showcase_video/render_remote.sh v2_surface v2s/scroll,v2s/uv   # 2 beats: ~1 min
PB_SHOWCASE_LAYOUT=showcase_video/layouts/tour.cfg \
  ./showcase_video/render_remote.sh v2_create,v2_edit,v2_surface,v2_tools,v2_map
```

`render_remote.sh` syncs the repo to `lame`, draws the editor on its idle
RX 570 through a headless Weston (kiosk shell) + Godot's Wayland driver, and
pulls back exactly the shots it re-recorded. Same window (1920x1080), same
viewport (1346x783), same pinned layout as a local render.

Measured (v0.9.191): a 156-frame shot took 43.4 s with the old local render,
11.4 s locally once the PNG encode was threaded, 3.6 s on lame. Before, the
cost of a frame was ~230 ms of single-threaded PNG encoding + ~50 ms of
llvmpipe; the encode now runs on the WorkerThreadPool (`_grab`), and the GPU
removes the draw. `render.log` prints `per-frame ms: draw / readback /
save-queue` every 300 frames — look there before guessing at a slowdown.

Gotchas, each one cost a round:
- **`DRI_PRIME` must be set for Godot itself**, not only for Weston: without
  it Godot picks the 7800 XT, which runs the LLM server, and the render
  stalled at boot. The log's `Using Device:` line must say RX 570.
- **`--fixed-fps 60` is mandatory** (render.sh passes it). Without it the
  editor's `_process(delta)` and shader `TIME` run on WALL time: every
  scroll, particle and water animation played at a speed set by how slow the
  render machine was (15x too fast under llvmpipe + inline PNG).
- ssh joins its arguments into one string: quote with `printf %q` (an empty
  argument vanished and shifted the rest).
- Never `pkill -f <pattern>` over ssh: the pattern matches the ssh shell's
  own command line. Use the pidfile (`$RDIR/weston.pid`).

Local renders (`render.sh`, Xvfb + llvmpipe) still work, for when lame is
busy; they are ~3x slower.

## Review with strips, not the review sheet

The review sheet (`out*/review-sheet.png`) shows ONE frame per clip. It cannot
show the failures the owner kept finding: a texture that never moves, a cut
that lands mid-action, a panel hidden under a caption. Use the strips:

```bash
cd showcase_video && PYTHONPATH=tools .venv/bin/python -m showcase.strip \
  shot v2_surface v2s/scroll --crop 287,44,1633,918 --motion   # a recorded take
  ... strip shot v2_create v2c/edge --from 3.0 --to 4.5          # find an in/out point
  ... strip seg l42-scroll --motion                              # a BUILT clip
  ... strip edl showcase_video/edl_v2.toml --only s11-edge       # clips of a cut
```

N timestamped frames; the LAST frame (the cut) is outlined red; `--motion`
adds a frame-difference row (black = nothing moves). Read every strip of a
beat you touched, and of the clip in the cut that uses it, before claiming it
works. Questions a strip answers that a sheet cannot:
- Does the action FINISH before the red frame? (s11-edge cut mid-wall.)
- Is the thing the caption names visible, and not under the caption?
- Does the animated thing move while the camera is STILL? Under a moving
  camera everything moves; the scroll beat read as "never starts" because the
  camera swung right after Apply.

## Checks must observe the effect, not the flag

`d.check(plugin.animate_scrolling_textures, ...)` passed for two rounds while
the sheet's scroll speed was (0, 0). A check names what the VIEWER should see
and measures that: the rendered material's `uv1_offset` changing, the mesh
positions returning, the panel's rect. The scroll bug itself: the Apply button
was at y=1177 in a 1080 window (scrolled out of the dock), so the click hit
nothing. `click_control` now refuses off-window targets and wheels them in
with `d.reveal(control)` (a real mouse-wheel scroll over the dock's
scrollbar; a wheel over a SpinBox changes the value instead).

Other director facts:
- `d.key()` moves focus to the 3D viewport first (right for shortcuts). To
  type into a dock field, click it and send keys straight to it (see
  `v2_surface.gd` `_field_key` / `_type`); setting `SpinBox.value` from code
  while its field has focus is overwritten by the stale text on focus-out.
- Element drags (`move_selection`) follow the projected pointer and land
  0.1-0.2 m off the request; a "move it back" drag does not return exactly.
  Put an element back with Ctrl+Z (`v2_edit.gd` `_move_back`).
- `build.sh --lint` lists clips that show a `fallback()`; run it after every
  re-render.

## FilmCraft: evaluated, not adopted (v0.9.191)

FilmCraft (storytold/filmcraft 0.20.1, `~/.local/bin/filmcraft-cli`, an
alpha Rust NLE with a CLI/MCP control surface) was tried as a review aid: its
scene-edit detection found 5 of ~18 cuts in the README cut (the clips are
crossfades between near-identical editor UI), and its timeline model
duplicates what the EDL already is. Rendering frames at times is what
`showcase.strip` does with ffmpeg. Re-evaluate only for a new need (e.g.
hand-editing a timeline with audio), not for review.
